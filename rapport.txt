1. VUE D'ENSEMBLE DU PROJET
================================================================================

EcomPilot est une plateforme SaaS (Software as a Service) complète destinée aux
entrepreneurs, PME et grandes entreprises tunisiennes et francophones. Elle offre
un écosystème intégré couvrant l'ensemble du cycle de vie commercial : de la
création d'une boutique en ligne à la gestion des commandes, de la comptabilité,
du marketing, et de l'intelligence artificielle.

OBJECTIF PRINCIPAL :
Fournir une alternative locale et compétitive aux grandes plateformes
internationales (Shopify, Wix, etc.) avec un focus sur :
- Le marché tunisien (monnaie TND, adresses locales, SMS, paiement COD)
- La facilité d'utilisation pour les non-techniciens
- La multi-location (chaque client = un tenant isolé)
- Un écosystème complet évitant la dépendance à des outils tiers

CONCURRENTS VISÉS :
- Converty-shop (Tunisie)
- Shopify / WooCommerce (international)
- Wix / Squarespace (création de sites)

LANGUES SUPPORTÉES : Français, Arabe (prévu), Anglais

2. ARCHITECTURE TECHNIQUE
================================================================================

BACKEND (NestJS - Node.js)
---------------------------
- Framework : NestJS (TypeScript)
- Base de données : MongoDB (Mongoose ODM)
- Authentification : JWT (JSON Web Tokens)
- Architecture : Modules découplés par domaine métier (44 modules)
- Multi-Tenancy : Isolation par tenant via TenantGuard
- API Style : REST (décrit ci-dessous par module)
- Fichier principal : backend/src/app.module.ts

MODULES BACKEND (44 modules) :
  abandoned-cart, accounting, ads-connectors, ai, alerts, analytics, auth,
  billing, booking, budgets, cart, coupons, currency, customers, debug,
  discounts, email, email-marketing, export, financing, import, integrations,
  inventory, marketing, notifications, onboarding, orders, payment, products,
  purchase_orders, rasa, reviews, sales, search, shipping, staff, store,
  subscriptions, tenants, upload, users, voice-calls, website, whatsapp

FRONTEND (React + TypeScript)
------------------------------
- Framework : React 18 + TypeScript
- Build Tool : Vite
- Routing : React Router DOM v6
- État Global : React Context (Auth, AI, Currency, Theme, Onboarding)
- HTTP Client : React Query (@tanstack/react-query)
- UI Components : Headless UI + Tailwind CSS
- Nombre de pages : 53 pages distinctes

DÉPLOIEMENT :
- Backend : Port 3000 (API NestJS)
- Frontend : Port 5173 (Vite Dev Server)
- Base URL API : /api/v1/

3. MODULE D'AUTHENTIFICATION & GESTION DES UTILISATEURS
================================================================================

FICHIERS CLÉS :
- backend/src/modules/auth/
- backend/src/modules/users/
- frontend/src/pages/LoginPage.tsx
- frontend/src/contexts/AuthContext.tsx

FONCTIONNALITÉS :

3.1 Inscription & Connexion
  - Création de compte avec email + mot de passe
  - Connexion sécurisée via JWT access tokens
  - Refresh tokens automatique pour maintenir la session
  - Hachage des mots de passe (bcrypt)

3.2 Gestion des Rôles
  - SUPER_ADMIN   : Accès total à toutes les ressources
  - ADMIN         : Gestion complète de son tenant
  - USER          : Accès limité aux fonctions de base
  Chaque rôle est enforced côté backend via des Guards NestJS.

3.3 Multi-Tenant par Utilisateur
  - Chaque utilisateur appartient à un tenant (entreprise)
  - Les données de chaque tenant sont totalement isolées
  - Le tenant ID est extrait du JWT à chaque requête

3.4 Profil Utilisateur
  - Page dédiée : /profile
  - Modification du nom, email, mot de passe
  - Préférences de thème (clair / sombre)

UTILITÉ :
  Garantit que chaque client de la plateforme a son espace dédié, sécurisé et
  indépendant des autres clients. La base de la sécurité de tout le système.

FONCTIONNALITÉS :

6.1 Réception des Commandes
  - Les commandes arrivent depuis la boutique publique ou le POS
  - Notification instantanée lors d'une nouvelle commande
  - Horodatage, liste des produits commandés, montant total

6.2 Gestion du Statut
  - Statuts : Nouvelle → En cours → Expédiée → Livrée → Annulée → Remboursée
  - Mise à jour manuelle ou automatique

  - Pour les commandes COD, un SMS OTP est envoyé au client
  - Le client doit confirmer son numéro via le code reçu
  - Sécurise les commandes contre les fausses commandes
  - Endpoint public de vérification : POST /api/v1/public/website/:slug/verify-otp

6.5 Facturation
  - Génération de factures PDF automatiques
  - Envoi de la facture par email au client
  - Accessible depuis /quotes

  - Gestion des commandes auprès des fournisseurs
  - Suivi des livraisons fournisseurs
  - Accessible depuis /purchase-orders

UTILITÉ :
  Module central du commerce. Chaque vente génère une commande qui doit être
  traitée, suivie et archivée. Le système OTP pour COD est particulièrement
  important pour le marché tunisien où le paiement à la livraison est dominant.

15.1 Modal Checkout Express (Boutique Publique)
  Technologie : Alpine.js embarqué dans la page générée
  - Modal qui s'ouvre sur clic "Commander" d'un produit
  - Formulaire d'information client adapté au marché tunisien :
    * Nom et prénom (obligatoires)
    * Numéro de téléphone tunisien (format +216 XX XXX XXX)
    * Gouvernorat (liste déroulante des 24 gouvernorats tunisiens)
    * Délégation (filtrage dynamique selon le gouvernorat)
    * Adresse détaillée (rue, numéro, etc.)
  - Choix du mode de paiement :
    * Paiement à la livraison (COD) - principal pour la Tunisie
    * Carte bancaire via Stripe (international)
    * Virement bancaire
  - Affichage du prix en TND (ملم) par défaut, avec conversion possible

15.2 Flux de Commande COD avec OTP
  Étape 1 : Le client remplit le formulaire de checkout
  Étape 2 : Soumission de la commande → backend reçoit la requête
  Étape 3 : Système génère un OTP à 6 chiffres + expiration (10 minutes)
  Étape 4 : SMS envoyé au numéro de téléphone du client avec le code
  Étape 5 : Client entre le code dans le formulaire (champ OTP affiché)
  Étape 6 : Vérification du code → commande confirmée
  Endpoint : POST /api/v1/public/website/:slug/order
  Endpoint : POST /api/v1/public/website/:slug/verify-otp

15.3 Sécurité des Commandes COD
  - Sans OTP, la commande reste "En attente de vérification"
  - Protection contre les fausses commandes (problème majeur en Tunisie)
  - Expiration du OTP après 10 minutes
  - Limite de tentatives de vérification

15.4 Checkout Admin (Interface Interne)
  Route : /checkout (interface admin)
  - Création manuelle de commandes par les agents
  - Sélection du client depuis la base de données
  - Ajout de produits avec quantités
  - Calcul automatique avec remises + TVA

15.5 Devise Tunisienne (TND)
  - Affichage par défaut en Dinars Tunisiens (TND)
  - Symbole : DT ou TND
  - Conversion automatique depuis d'autres devises
  - Formatage local : 1 250,500 TND

UTILITÉ :
  Le checkout express est le cœur de la conversion. Un formulaire trop long ou
  inadapté fait fuir les acheteurs. L'adaptation au marché tunisien (gouvernorats,
  COD, OTP, TND) est un avantage compétitif direct face aux plateformes
  internationales qui ne localisent pas suffisamment.

21. SÉCURITÉ & MULTI-TENANCY
================================================================================

21.1 Architecture Multi-Tenant
  - Chaque entreprise = 1 tenant avec son propre espace de données
  - Isolation totale : tenant A ne peut jamais voir les données de tenant B
  - Implémenté via TenantGuard NestJS sur toutes les routes protégées
  - Le tenant ID est encodé dans le JWT à la connexion

21.2 Authentification JWT
  - Access Token (courte durée : 15 minutes)
  - Refresh Token (longue durée : 7 jours)
  - Rotation automatique des tokens
  - Révocation possible (logout, changement de mot de passe)

21.3 Autorisation par Rôles (RBAC)
  - Guards NestJS : RolesGuard, TenantGuard, AdminGuard
  - Vérification server-side sur chaque endpoint
  - Pas de confiance en le frontend pour la sécurité

21.4 Validation des Données
  - DTOs (Data Transfer Objects) avec class-validator
  - Sanitization des entrées utilisateur
  - Protection contre les injections NoSQL (MongoDB)

21.5 Sécurité des Paiements
  - Les clés API Stripe ne sont jamais exposées côté client
  - Les tokens Stripe sont gérés server-side
  - HTTPS obligatoire en production

21.6 OTP & Verification
  - Codes OTP à usage unique avec expiration
  - Protection contre le brute-force (limite de tentatives)

UTILITÉ :
  La sécurité est non-négociable dans un SaaS commercial manipulant des données
  de paiement et des informations clients sensibles. L'architecture multi-tenant
  garantit l'isolation et la confidentialité des données de chaque client.
